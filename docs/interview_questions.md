# Interview Preparation Guide: RAG & LLM Concepts

This guide contains answers to 25 essential questions about Retrieval-Augmented Generation (RAG), vector databases, embeddings, and LLM orchestration, structured to help you succeed in technical interviews.

---

## 1. What is RAG?
* **Concise Answer**: RAG (Retrieval-Augmented Generation) is an architectural pattern that enhances a Large Language Model's capabilities by fetching relevant context from an external data source (like a PDF) and injecting it into the prompt. This allows the LLM to answer questions using private or real-time data without needing retraining.
* **Detailed Explanation**: Traditional LLMs are limited to the knowledge present in their training data up to a specific cutoff date. RAG solves this by implementing a two-step process: (1) **Retrieval**: searching a document index for text blocks matching the user's query, and (2) **Generation**: sending the query along with the retrieved text blocks as a "ground truth" reference to the LLM. It transforms the generation task from a closed-book recall exercise into an open-book comprehension task.

---

## 2. Why did you use RAG instead of fine-tuning?
* **Concise Answer**: I used RAG because it is cheaper, faster, allows dynamic updates to the document database without retraining costs, provides perfect source traceability (citations), and is significantly more effective at reducing factual hallucinations.
* **Detailed Explanation**: 
  - **Dynamic Knowledge**: With RAG, adding, updating, or deleting a PDF is as simple as updating files in a local directory or vector database. Fine-tuning requires running training loops on GPU clusters, which is slow and expensive.
  - **Factual Traceability**: Fine-tuning teaches a model style, tone, or specific formatting, but it is notorious for leaking or hallucinating facts. RAG provides the exact source text, making responses auditable and verifiable.
  - **Resource Efficiency**: Fine-tuning requires massive labeled datasets and compute hardware. RAG can run on standard consumer hardware by outsourcing the heavy generative work to hosted APIs (like Groq) while keeping parsing local.

---

## 3. What is an embedding?
* **Concise Answer**: An embedding is a high-dimensional vector (a list of decimal numbers) generated by a specialized neural network that represents the semantic meaning of a word, sentence, or document chunk.
* **Detailed Explanation**: In RAG, we convert text into embeddings so that computers can perform mathematical comparisons on meaning. An embedding model (like `all-MiniLM-L6-v2`) projects a text block into a continuous vector space. If two sentences are semantically similar (e.g., *"The weather is gorgeous"* and *"It is a beautiful sunny day"*), their vectors will point in almost the same direction in vector space, yielding a high cosine similarity, even if they share no words in common.

---

## 4. Why did you use `all-MiniLM-L6-v2`?
* **Concise Answer**: It is a highly efficient, lightweight sentence-transformer model that outputs 384-dimensional embeddings. It runs extremely fast on standard CPUs, making it ideal for standard developer setups without dedicated GPUs.
* **Detailed Explanation**: In production systems, choosing an embedding model is a trade-off between latency, model size, and retrieval quality. `all-MiniLM-L6-v2` is a standard benchmark model for sentence similarity. Its small size (approx. 80MB) means it loads instantly and consumes minimal RAM. The 384-dimensional output keeps the FAISS index small, allowing for extremely fast similarity searches on a local CPU.

---

## 5. Why did you use FAISS?
* **Concise Answer**: FAISS (Facebook AI Similarity Search) is a lightweight, open-source library optimized for vector similarity search on CPU. It is saved directly to local files, which removes the network latency and cost of cloud vector databases.
* **Detailed Explanation**: For session-based or single-developer environments, a cloud vector database (like Pinecone) introduces network overhead and API configurations. FAISS compiles directly to C++ with Python bindings. It computes L2 (Euclidean) distances between query and chunk vectors in microseconds. Because FAISS can persist its index locally as a set of flat files, we can isolate user collections using simple session folder structures.

---

## 6. What is semantic search?
* **Concise Answer**: Semantic search seeks to understand the searcher's intent and the contextual meaning of documents, rather than matching exact keywords like a traditional `Ctrl+F` or database query.
* **Detailed Explanation**: Keyword search (lexical search) searches for exact string characters. If a user asks *"How do you fix a flat tire?"*, a keyword index might fail to return a document titled *"Replacing a punctured wheel"* because none of the words match. Semantic search translates both the question and the documents into embedding vectors and uses distance metrics to retrieve the document because the underlying concept is identical.

---

## 7. What is chunking?
* **Concise Answer**: Chunking is the process of breaking down a large text document (like a 100-page PDF) into smaller, coherent, and manageable blocks of text prior to embedding and indexing.
* **Detailed Explanation**: Chunking is required because:
  - **Context Window Limitations**: Embedding models and LLMs have finite input token limits.
  - **Retrieval Precision**: If we embedded an entire book as a single vector, the specific details would be averaged out and lost. Splitting text into small chunks allows us to pinpoint the exact paragraph containing the answer.
  - **LLM Context Density**: Feeding the LLM only the relevant 800-character blocks keeps the prompt dense, making response times faster and reducing generation costs.

---

## 8. Why use chunk overlap?
* **Concise Answer**: Chunk overlap ensures that semantic context which crosses a boundary is not lost or split in half, preserving continuity between adjacent chunks.
* **Detailed Explanation**: When text is split, a sentence might be cut mid-thought. For example:
  - Chunk 1: *"...the solution to this equation is"*
  - Chunk 2: *"$x = 42$. This defines..."*
  Without overlap, Chunk 1 has no context of the value, and Chunk 2 has no context of what $x=42$ refers to. An overlap (e.g., 150 characters) ensures that the transition text resides in both chunks, maintaining semantic completeness.

---

## 9. How did you choose chunk size?
* **Concise Answer**: I chose `800` characters with a `150` character overlap as a standard baseline, balancing the trade-off between semantic integrity (size) and retrieval granularity.
* **Detailed Explanation**: 
  - **Too Small Chunks (e.g., 100 chars)**: Slices sentences and loses context, making it hard for the embedding model to represent the true meaning.
  - **Too Large Chunks (e.g., 4000 chars)**: Dilutes the specific topic and fills the LLM context window with irrelevant information, increasing costs and response times.
  - **Choice**: 800 characters translates to roughly 120-150 English words, which is generally equivalent to 1-2 cohesive paragraphs. This is the optimal length for retrieving specific answers.

---

## 10. What is top-k retrieval?
* **Concise Answer**: Top-k retrieval is the configuration that dictates how many of the most semantically relevant document chunks are retrieved from the vector database to be sent to the LLM.
* **Detailed Explanation**: If `top_k = 4`, the vector database calculates the similarity scores for all chunks and returns only the 4 chunks with the lowest distance (highest similarity) to the user's question. A higher `k` provides more context but increases costs and token usage, while a lower `k` is faster but might miss auxiliary information.

---

## 11. What happens when a user asks a question?
* **Concise Answer**: The system embeds the question, retrieves the top-k closest chunks from the FAISS database, constructs a system prompt containing these chunks alongside grounding instructions, and queries the Groq API to generate a factual response.
* **Detailed Explanation**: The pipeline flow:
  1. The user's text question is converted into a vector embedding using `all-MiniLM-L6-v2`.
  2. FAISS performs an L2 distance search to select the top-k document chunks.
  3. The system structures the prompt, embedding the retrieved texts in a designated `Context` block.
  4. The prompt is sent to Groq with `temperature=0.0`.
  5. The LLM returns the response, and page citations are rendered programmatically from the chunk metadata.

---

## 12. How does the system reduce hallucinations?
* **Concise Answer**: By using strict system prompts (grounding rules) that instruct the LLM to only answer based on the provided context, setting the temperature to `0.0`, and programmatically extracting citations rather than letting the LLM invent them.
* **Detailed Explanation**:
  - **System Prompt Constraints**: Instructions explicitly command the model: *"If the answer is not available in the provided context, say 'I could not find this information...'"*.
  - **Deterministic Temperature**: Setting `temperature=0.0` forces the LLM to choose the highest-probability tokens. This removes the randomness that often leads to creative fabrication.
  - **Programmatic Citations**: The citation list is generated directly from the database search metadata, preventing the model from inventing plausible-sounding source pages.

---

## 13. Can RAG completely eliminate hallucinations?
* **Concise Answer**: No, RAG reduces hallucinations significantly, but it does not completely eliminate them. The LLM can still misinterpret the retrieved text or yield logical errors.
* **Detailed Explanation**: Hallucination risks still exist if:
  - The retrieved text is ambiguous, causing the model to misinterpret it.
  - The prompt is poorly structured, and the LLM bypasses the system rules due to prompt injection or model limitations.
  - The model performs complex reasoning over the context and makes mathematical or logical inference mistakes.

---

## 14. What are the limitations of this project?
* **Concise Answer**: It lacks OCR (cannot read scanned text PDFs), does not process tables or images within PDFs, lacks a persistent multi-user database, and relies entirely on a hosted LLM API (requiring internet access).
* **Detailed Explanation**:
  - **Extraction Limits**: PyMuPDF extracts text, not layout or drawings. Images and scanned documents (image-only PDFs) return empty text.
  - **Simple Chunking**: Recursive text splitting is text-only and doesn't understand table structures, which can destroy the semantic relationships of rows and columns.
  - **No Reranking**: It retrieves chunks based on raw vector similarity, which may not always capture the exact nuances needed for complex queries.

---

## 15. How would you improve retrieval?
* **Concise Answer**: I would implement hybrid search (keyword + semantic search), add a cross-encoder reranker, and apply advanced chunking strategies like parent-child chunking.
* **Detailed Explanation**:
  - **Parent-Child Chunking**: Store small chunks for vector similarity search (as they capture narrow semantics better) but retrieve and send their larger parent paragraphs to the LLM (providing broader context).
  - **Metadata Filtering**: Allowing users to filter searches by file name or date to narrow down the search space before running similarity matching.

---

## 16. How would you add hybrid search?
* **Concise Answer**: Hybrid search combines keyword-based search (like BM25) with vector-based semantic search, merging their results using a method like Reciprocal Rank Fusion (RRF).
* **Detailed Explanation**: While semantic search excels at concepts, it can fail at searching for exact serial numbers, product codes, or specific names. BM25 (based on Term Frequency-Inverse Document Frequency) excels at matching exact keywords. Running both searches in parallel and merging their rankings ensures the system captures both conceptual similarity and exact keyword matches.

---

## 17. How would you add reranking?
* **Concise Answer**: I would use a lightweight Cross-Encoder model (like Cohere Rerank or BGE-Reranker) to evaluate the top 25 retrieved chunks and select the top 4 most relevant ones.
* **Detailed Explanation**: Vector similarity search (Bi-Encoder) encodes the query and documents separately, which is fast but can miss complex query-document interactions. A Reranker (Cross-Encoder) processes the query and document chunk *together* through a transformer layer, calculating a much more accurate relevance score. Since it is computationally heavy, we run it as a second-stage filter on only the top retrieved results.

---

## 18. How would you scale the application?
* **Concise Answer**: I would replace FAISS with a distributed cloud vector database (like Pinecone, Qdrant, or Milvus), move ingestion to background worker queues (like Celery), and containerize the app using Docker.
* **Detailed Explanation**: Local files do not scale when thousands of users upload documents simultaneously. Moving to a dedicated vector database enables horizontal scaling, indexing millions of vectors with low latency. Decoupling the PDF processing from the main Streamlit thread using background workers prevents UI freezes during heavy uploads.

---

## 19. Why use a hosted LLM?
* **Concise Answer**: Hosted APIs (like Groq) execute model inference on high-end hardware (like NVIDIA H100s or LPUs) in milliseconds, allowing complex models to run on standard laptops without requiring a local GPU.
* **Detailed Explanation**: Running a model like Llama-3 8B locally requires at least 8-16 GB of dedicated VRAM and consumes significant battery and CPU resources. A hosted provider handles these requirements at scale, allowing our local app to remain extremely lightweight and portable.

---

## 20. What would change for local LLM inference?
* **Concise Answer**: I would replace the Groq API client with a local inference engine like Ollama or llama.cpp, using a quantized model (e.g. Llama-3 8B Q4) running on the local host.
* **Detailed Explanation**: The code changes would involve redirecting the HTTP client to a local port (e.g., `http://localhost:11434/v1` for Ollama's OpenAI-compatible API). Since local CPU execution is slow, we would use quantized models (GGUF format) which reduce model precision (from 16-bit to 4-bit) to make execution feasible on standard consumer RAM.

---

## 21. How would you deploy the application?
* **Concise Answer**: I would package the application using Docker, deploy the container to a cloud platform like AWS ECS, Google Cloud Run, or Streamlit Community Cloud, and load secrets using secret manager services.
* **Detailed Explanation**: Containerization ensures that Python version mismatches, OS dependencies (like FAISS C++ binaries), and library variables are locked. A service like Google Cloud Run provides serverless container execution, automatically scaling down to zero instances when the app is idle, minimizing hosting costs.

---

## 22. How would you evaluate RAG quality?
* **Concise Answer**: I would use a framework like Ragas or TruLens to measure quantitative metrics: Faithfulness (is the answer based on context?), Answer Relevance (does it answer the query?), and Context Recall (was the correct information retrieved?).
* **Detailed Explanation**: Evaluating RAG requires decoupling retrieval and generation:
  - **Retrieval Evaluation**: Measures *Mean Reciprocal Rank (MRR)* or *Hit Rate* using a test set of questions and ground-truth document pages.
  - **Generation Evaluation**: Uses LLM-as-a-judge to evaluate:
    - *Faithfulness*: Percentage of sentences in the generated answer that can be mathematically inferred from the context.
    - *Answer Relevance*: Semantic similarity between the user's question and the generated answer.

---

## 23. What is the difference between an embedding model and an LLM?
* **Concise Answer**: An embedding model converts text into a fixed-size numerical vector representing its meaning (encoder), while a generative LLM takes a text prompt and generates new human-like text sequence predictions (decoder).
* **Detailed Explanation**: They perform fundamentally different operations:
  - **Embedding Model** (e.g., `all-MiniLM-L6-v2`): It is an *Encoder* network. Its job is to output numbers. Input: "cat" -> Output: `[0.12, -0.45, 0.88, ...]`.
  - **Generative LLM** (e.g., Llama-3): It is a *Decoder* or *Encoder-Decoder* network. Its job is to output words. Input: "Describe a cat" -> Output: "A cat is a small carnivorous mammal..."

---

## 24. How do you preserve source citations?
* **Concise Answer**: Citations are preserved by binding source and page number metadata directly to the text chunks during splitting. The citations are compiled programmatically from the retrieved vectors rather than letting the LLM generate them.
* **Detailed Explanation**: When PyMuPDF parses a page, it yields a page number. The text splitter attaches this metadata to every sub-chunk. When FAISS retrieves the matching chunks, it returns the metadata objects alongside the text. We extract the unique source-page combinations from these metadata blocks and render them directly in the UI, ensuring 100% citation reliability.

---

## 25. What would you change for an enterprise system?
* **Concise Answer**: I would add enterprise-grade authentication, role-based access control (RBAC), end-to-end data encryption, audit logging, file ingestion pipelines with OCR (like Unstructured or AWS Textract), and a distributed vector database.
* **Detailed Explanation**: Enterprise requirements go far beyond basic RAG:
  - **Access Control**: Users must only retrieve document chunks they have permissions to view. This requires embedding document access control lists (ACLs) directly into the metadata and applying pre-filtering during vector searches.
  - **Data Privacy**: Uploads must go through DLP (Data Loss Prevention) scanners to strip PII (Personally Identifiable Information) before indexing.
  - **High Availability**: Decoupling services into microservices (Parser Service, Vector Service, Query Service) running on Kubernetes.
